# Mobile notification rendering

## iOS service extension

An iOS notification service extension runs in its own process before an eligible remote alert is presented. The application delegate and a silent push cannot provide this entry point. The sender must use an APNs alert with `aps.mutable-content` equal to `1`, a safe non-sensitive `aps.alert`, and encrypted application data in custom payload fields.

The extension's Rust crate declares `crate-type = ["staticlib"]` and one callback, shown here for fixed-text rendering.

```rust
use pushups::{Error, Message, Notification, RenderingContext};

#[pushups::notification_service]
fn render(context: RenderingContext, message: Message) -> Result<Notification, Error> {
    if context.is_cancelled() {
        return Err(Error::Platform("notification rendering expired".into()));
    }
    let data = String::from_utf8(message.payload)
        .map_err(|error| Error::Platform(error.to_string()))?;
    Ok(Notification::new("New activity").data(data))
}
```

Application-produced and encrypted rendering supply application-owned interpretation or decryption in that callback. `pushups` supplies no encryption, key storage, payload schema, network client or async runtime. The callback receives owned bytes containing the complete original APNs user-info dictionary as `JSON`, and `Message.started_app` is `false` because the extension does not launch the application.

The callback runs on an extension-owned worker. `RenderingContext` is `Clone + Send + Sync` and contains an owned request identifier, a monotonic deadline and shared completion state, with `request_id()`, `deadline()`, `is_cancelled()` and `outcome()` accessors. Consumer async work must run on its own executor and obey the deadline and cancellation signal, without retaining native references.

Completion selects one terminal outcome exactly once. The bound is 25 seconds from receipt or the earlier platform expiration callback. Cancellation is cooperative, and work that returns after completion cannot change the notification.

| Outcome | Presented content |
|---|---|
| `Rendered` | Returned title and body |
| `Failed` | Original safe alert |
| `Panicked` | Original safe alert after an unwinding panic |
| `Expired` | Original safe alert |
| `WorkerUnavailable` | Original safe alert |
| `Superseded` | Original safe alert for the displaced request |

The final outcome is stored in the `pushups.rendering-outcome` user-info string. Abort-mode panics and process termination cannot run Rust cleanup, and iOS retains its original-alert fallback. The original alert must therefore remain safe to show without decryption.

A successful `Notification` replaces title and body, with an absent body clearing the body. `tag` maps to the native thread identifier, and `data` and `navigate` occupy reserved user-info keys while unrelated user info, attachments, badge, sound and category remain intact. Icon URLs are unsupported on mobile and select failure rather than fetching media.

### Bundle and signing

Compile the shipped `ios/PushupsNotificationService.swift` into the extension and link the consumer's Rust static library. The Swift adapter calls the Rust receive and expiration symbols generated by `#[pushups::notification_service]`. Its module-qualified `PushupsNotificationService` class is the extension's principal class.

The `.appex` belongs in the application's `PlugIns` directory. Its property list needs `NSExtensionPointIdentifier = com.apple.usernotifications.service` and `NSExtensionPrincipalClass = <SwiftModule>.PushupsNotificationService`. Link `Foundation` and `UserNotifications`, compile with application-extension restrictions, and use compatible application and extension deployment targets.

Device builds require a distinct extension bundle identifier and matching provisioning profile. Sign the extension before its containing application with compatible identities and entitlements. The extension does not inherit the application's entitlements or its container.

Shared files require the same App Group entitlement on both targets. Shared keys require an explicitly shared keychain access group and a key accessibility policy that permits locked-device notification processing. A biometric-protected replica key remains outside the extension's rendering path.

[Dioxus app-extension tooling](https://github.com/DioxusLabs/dioxus/pull/5896) supplies `[[ios.app_extensions]]`, `rust_crate`, `frameworks`, module-qualified principal classes and nested signing. Point `source` at the Swift extension sources, `rust_crate` at the consumer's static-library crate, `extension_point` at `com.apple.usernotifications.service`, and `principal_class` at `PushupsNotificationService`. This capability depends on that tooling contribution, rather than released `dx` support being assumed.

Tauri and direct `tao` or `winit` applications embed the same native extension target in their Apple project and link the Rust static library. Their build tooling owns target creation, embedding, provisioning and signing. The application's APNs entitlement and registration remain separate from service-extension packaging.

## Android presentation

An Android data-message handler can call `Notification::show` without a foreground `Activity`. Presentation uses retained process state and attaches the calling Rust thread to the JVM. Android 8 and later use the `pushups` channel with the application label and default importance.

The application icon supplies the small icon, with a platform icon as the fallback when the application has none. Denied notification permission, disabled notifications or channel, a missing launcher, and an icon URL return an error. Presentation never fetches an icon URL.

An exact `tag` replaces the corresponding notification, while an absent `tag` gives each notification an independent identity. An immutable `PendingIntent` explicitly opens the application's launcher with the navigation URL and exact UTF-8 `data`, including an empty string. Without `data`, the tap opens the application without generating a tap message.

Tap data reaches `Event::Message` through the foreground delivery path and never invokes the background handler. Lifecycle re-creation does not deliver it twice. `Message.started_app` is `true` for a tap that creates the process's first `Activity` when no earlier push has arrived, and is `false` after a headless push or in a live foreground session.

The `Context` passed to `#[pushups::background_handler]` borrows the native callback, so it cannot outlive the handler or leave its thread. On Android, `Context::with_jni` lends the callback's JNI `0.21` environment and the `android.content.Context` the push arrived on. The closure can return a global reference or anything built from one, such as an explicit key-store context, while its local references stay inside it. `Notification::show` uses the retained runtime independently of the callback.

## Acceptance boundary

`ci/apple/run.sh` exercises native transformation and completion on macOS, then links and verifies Rust entry symbols in ad-hoc-signed iOS device and simulator extension bundles. The harness does not execute an iOS extension in the simulator or establish locked-iPhone alert delivery, background scheduling, real keychain accessibility or visible locked-device rendering, which require device acceptance.

`ci/android/rendering.sh` exercises headless presentation, refusal cases, tagged replacement, launcher tap delivery and the context `with_jni` lends on a booted Android device or emulator.

`ci/android/compile-contract/check.sh` type-checks an Android app that forbids `unsafe` code and confirms that keeping the `Context`, sending it to another thread or returning a local reference from `with_jni` fails to compile.
